Ocado OSP: OAuth chain vs open redirect

What we actually measured on www.ocado.com / sso.ocado.com (Intigriti, 2026-08-17). Verdict: no confirmed open redirect and no stolen authorization code.

1. What these words mean

Open redirect: the server (or a script it shipped) sends the browser to a host the attacker picked. Proof is a Location header or window.location whose host is not Ocado.

OAuth authorization code: a one-time string Salesforce puts on https://www.ocado.com/sso-login?code=… after you log in. If that code lands on attacker.com, they can try to finish login as you.

Why they pair: textbook steal is redirect_uri = an open redirect on a trusted host. The code follows the bounce.

Need: HTTP status + Location, or a browser URL. Seeing example.com in a JS file is not a redirect.

2. Map of this login

browser
  → www.ocado.com/login?destination=/path
      cookies: sso.state, sso.codeVerifier, sso.nonce (HttpOnly)
  → sso.ocado.com/services/oauth2/authorize
      redirect_uri is always https://www.ocado.com/sso-login
  → /ocado/login  (Google / Facebook / PayPal / Apple)
      JS may copy startURL into sessionStorage and social links
  → www.ocado.com/sso-login?code=…&state=…
  → /sso-login/auth
  → 302 Location: decoded destination (path only)

Two different “where next?” values:

  • destination on www — encoded into OAuth state as web_<base64url>_<uuid>, replayed after code exchange.
  • startURL on Salesforce — where Salesforce thinks you should go after its login. Not the same filter.

3. “JS had example.com” — what that actually was

The first HTML of /ocado/login?startURL=https://example.com (~61 KB) contains zero example.com and zero startURL strings. The payload is not baked into the shell page.

The Lightning Web Runtime view (login_view, ~663 KB) contains example.com nine times. Every hit is a placeholder email, not our redirect:

emailPlaceHolder: "john.smith@example.com"
ssot__EmailAddress__c: "howard.jones@example.com"
… alice.smith / bob.wilson / …

That is demo data inside Salesforce Data Cloud sample objects. It does not navigate the browser.

The same view does implement startURL:

getStartUrlFromQueryParams() {
  return new URLSearchParams(location.search).get("startURL")
}
// social buttons:
sessionStorage.setItem("oauth_startURL", btoa(t))
location.href = origin + "/ocado/services/auth/sso/Google?startURL=" + encodeURIComponent(t)

So: the client forwards the query to Salesforce social endpoints. It does not location.assign("https://example.com"). We requested those social URLs with startURL=https://example.com: 401 or 500, no Location: https://example.com.

Password login would send startUrl to a Salesforce Apex action. We did not submit a password to complete that path; the GET of the login page still does not bounce.

accounts.ocado.com

Shop errors link to https://accounts.ocado.com/auth-service/sso/error-warn. That hostname has no DNS. Not an open redirect. ocodo.com (typo) is a parked 403 — not Ocado, not tested.

Leftovers (hail-mary, GET only, no scanner)

Intigriti forbids ZAP/Nessus and caps custom scripts at 3 req/s. Hail Mary here means leftover vectors, not ffuf floods.

  • /ocado/s/login/ 404; /s/login/ 401; community login 200; OIDC logout ignores attacker URI.
  • POST /logout on www: visitor 403/500. JSON logoutUrl never seen (needs a logged-in shop session). Logout CSRF is program-excluded anyway.
  • ?confirmRedirect= does nothing unless a CMS nav href contains it. Homepage had 0 such links.

6. Core questions

Did HTML/JS contain example.com? Login shell: no. View bundle: yes, only as @example.com placeholder emails. Our startURL=https://example.com string was not in either file.
Does the client still redirect? It only copies startURL to Salesforce or social ?startURL=. Server must emit a 3xx or location = to leave Ocado. It did not.
When is dest an open redirect? Only if after /sso-login/auth the browser’s host is not Ocado. Encoded slashes stayed on www.
Can we steal the code via redirect_uri? Not with this client_id. Mismatch is 400. Loose http/query match still redeemed to the registered HTTPS URI.
What failed first? AWS WAF 202 without aws-waf-token. Refresh from the Caido browser. Completing Google login leaves www for sso.ocado.com (now in scope if you continue).

7. What to take away

  1. Filter the string the server will put in Location, not the string sitting in a bundle as sample email data.
  2. Two hops (shop dest vs Salesforce startURL) means two filters. Killing one hop is not the whole chain.
  3. Location: /%2f%2fexample.com is still same-origin. Confirm in a real browser.
  4. A 302 to SSO is not an open redirect. Read the next Location after login.
  5. Dead hostnames in error URLs (accounts.ocado.com NXDOMAIN) are not takeovers under the parent zone.
